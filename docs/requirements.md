## 1. 引言

### 1.1 目的与范围
定义 ride-pro 网约车演示系统的业务需求、非功能需求、边界与验收标准。系统对标滴滴的领域拆分与司乘体验，覆盖乘客端、司机端、平台管理端三套 H5，以及与 payment-pro（支付）、cs-pro（客服）、ops-pro（运维）的跨系统集成。

### 1.2 读者
产品/研发/测试/运维。需求编号 `FR-*`（功能）与 `NFR-*`（非功能）用于追踪；实现证据指向 DESIGN.md 章节与验证脚本。

### 1.3 术语
| 术语 | 含义 |
|---|---|
| 双账本 | ride 本地钱包账本 + payment-pro 权威账本，经镜像同步保持增量一致 |
| 镜像 | ride 资金操作同步调用 pp OpenAPI → 回执 → 落 CONFIRMED 流水的两阶段过程 |
| outbox | 与业务同事务落事件表、异步投递 + 对账兜底的一致性机制 |
| 接力 | 多车型同呼时无人接单自动切换候选车型重新报价派单 |
| 支撑域 | ride-support，承载体验/运营公共能力（POI/券/安全/配置/RBAC 等） |
| 收银台 | payment-pro 开放 9 个 cashier.* 商户方法，由 ride 乘客端渲染的支付界面 |

## 2. 背景与目标

- **业务目标**：在一个可零依赖直接运行的仓库内，完整呈现网约车核心交易闭环（叫车→派单→接驾→行程→计价→支付→退款/提现）与滴滴级司乘体验、平台运营能力。
- **工程目标**：领域拆分清晰、资金一致性可验证、故障可自愈、文档与代码同仓同步。
- **硬约束**：默认零外部依赖（H2 文件库 + 内嵌 ZooKeeper，`./run.sh` 一键起）；Docker 双模式（`--docker` 接共享 MySQL/ZK）为用户拍板的例外；不引入 Seata/XA 等外部协调器；Netty 为进程内库例外。
- **协作定位**：六系统（ride/payment/cs/claim/yiwu/ops）端口错开可同跑；ride 不自建支付权威账本、不自建客服知识库，经开放接口集成。

## 3. 角色与场景

| 角色 | 入口 | 核心场景 |
|---|---|---|
| 乘客 | passenger.html | 选点叫车、多车型比价、券/加价/舒适偏好、行程跟踪、支付（余额/收银台）、评价、发票、会员、安全中心、IM、投诉 |
| 司机 | driver.html | 注册车辆、出车听单、抢单/拒单、导航接驾/送驾、完单计价、收入/提现、服务分/证件/培训、安全与运营任务 |
| 平台运营 | admin.html（RBAC：ADMIN/OPS/FINANCE/SUPPORT） | 总览大屏、订单处置、退款审批、流水/对账、outbox 重放、配置/券/活动、封禁、工单、审计、报表 |
| 客服 | cs-pro（外部） | 经 open API 接收 ride 投诉工单并回查状态 |
| 支付系统 | payment-pro（外部） | 权威账本、资金单、收银台开放方法、异步通知 |
| 运维 | ops-pro（外部） | 注册/启停/监控 ride 进程与中间件 |

## 6. 边界与未做项

**外部 SDK/真实通道（⛔，需资质/密钥/商用授权，用户拍板暂不接）**：真实接驾/送驾导航 SDK、虚拟号真实拨打、微信/支付宝/银行卡真实收单（收银台为 pp 沙箱通道）、人脸活体核验 SDK、多城市开通、报表定时订阅。

**演示取舍（🔶，生产修复方向见 DESIGN §14.2）**：直线距离近似路网计价；模拟驾驶代替真实 GPS 轨迹；人脸核验为确认+事件；机场排队/热区为演示数据；地图瓦片为免费栅格（非官方 JS API）。
